[S04 / incremental update] No explicit workspace backup before an `update`.
    GATK's own tracker (broadinstitute/gatk#6558) reports GenomicsDB workspace
    CORRUPTION when an incremental `--genomicsdb-update-workspace-path` run fails
    partway, and recommends backing the workspace up first. We have NOT verified
    this against GATK 4.6.2.0 and there is no snapshot/verify/swap guard in S04.
    Current partial mitigation (by luck of the design, not intent):
      - S04's `update` path copies the live workspace to /scratch and imports
        into the copy, so the on-/mnt/data original is untouched until copy-back.
      - copy-back is an atomic `mv` of a fully-staged `.<chr>.new.$$` dir over the
        old workspace — a crash DURING the mv is the only true danger window, and
        the old dir is gone at that point with no backup.
      - test01 (3 update waves, chr22) and test02 (1 update wave, chr1) both ran
        this way with no corruption. Small n, all on the JAGUAR test workspace.
    DEFERRED, but this is a PRE-CONDITION for the first PRODUCTION incremental:
    before the SLE update wave (JAGUAR's first full run is a single `create`, so
    it is not affected), add to S04's update path:
      1. snapshot the live workspace to <output>/<chrom>.bak.<ts> (or assert the
         scratch stage-in copy is complete + byte-count matches) BEFORE the gatk
         call;
      2. verify the new workspace after copy-back (SelectVariants smoke query /
         sample count) BEFORE removing the backup;
      3. on any failure, keep the backup and print the restore command.
    Track alongside the pipeline-wide checker (section 5) — the checker should
    also warn when `update` is requested and no recent backup exists.

 3. FENIX ARCHITECTURE — WHAT WE LEARNED (carry into 04/05/06)
-------------------------------------------------------------------------------

[scratch] (Sept-2026 benchmark, see INSTRUCTIONS.md)
    * Sequential, streaming GATK steps (MarkDuplicates, BQSR, HaplotypeCaller)
      are CPU-bound. Staging their large read-once inputs to /scratch gives NO
      wall-time benefit — it is pure copy-in overhead. Read those from NFS.
    * ALWAYS route TMPDIR + tool temp (samtools sort -T, gatk --tmp-dir, Spark
      local dir) to /scratch — that is the genuinely IOPS-heavy traffic.
    * GenomicsDBImport is the OPPOSITE case: the TileDB workspace does lots of
      small random reads/writes and should NOT live on NFS during the build.
      S04 builds the workspace on /scratch and copies the finished product
      back. This is a real benefit, not just quota hygiene.
    * Write bulky transient intermediates to /scratch, copy only finals back —
      keeps the group's persistent quota clean regardless of speed.

[resourcing] Keep per-job requests modest so jobs schedule fast:
    * S02  ~8 CPU / 32G   (MarkDuplicatesSpark heap + GC threads)
    * S03  SCATTER (default): 25-way SLURM array, one chromosome per task,
                            2 CPU / 13G / 48h, %6 concurrent, then a ~13-min
                            gather. Per-sample WALL ~3 h (was ~12 h whole-genome
                            — which was timing out against the old 12 h cap).
                            -Xms2G -Xmx10G per shard (chrY/chrM don't need 10G
                            committed). See section 4 "S03 SCATTER" for the
                            Batch16 measurements.
      S03 whole-genome (legacy, SCATTER_S03=false): ~4 CPU / 32G,
                            --native-pair-hmm-threads 4, -Xmx20G, ~12 h.
    * S04  2 CPU always (10-18% CPU eff at any core count — serial + I/O-bound).
                            RAM + wall-time SCALE WITH CONTIG SIZE (native TileDB
                            fragment data, not heap): chr22 6.7 GB/72 min,
                            chr1 27 GB/7.7 h create, chr1 32 GB/21 h update+consol.
                            Launcher scales --mem/--time by contig class
                            (chr1-2 64G/20h, chr3-8+X 32G/12h, rest 16G/6h);
                            GENDBI_BATCH_SIZE 50->25 halves import RAM. -Xmx6g.
    * S05  GenotypeGVCFs, per chromosome. Reading the GenomicsDB from /mnt/data
           (NFS) is I/O-BOUND: a SelectVariants smoke-test on chr1:1-500000 of
           the 93-sample db (test02) showed ~10x wall/CPU in the GenomicsDB
           iterator + an ~8 min one-time warm-up before it sped up. So S05 should
           STAGE THE WORKSPACE TO /scratch first (same as S04's build does) and
           read it from there. Est. many hours for chr1. ~2 CPU (serial-ish),
           mem scales with contig like S04 (start 32-48G for chr1).
    * S06  (est.) ~2 CPU / 24-32G, VQSR model building is memory-ish
    Scatter by chromosome and submit per-chrom jobs rather than one fat job.

 4. S04 GenomicsDBImport — DESIGN DECISIONS (implemented 2026-08-31)
-------------------------------------------------------------------------------

See docs/S04_GenomicsDBImport_design.md for the full rationale. Summary of the
choices made with the maintainer:

  1. Input contract  : explicit 2-column TSV sample map (label <TAB> chrom_gvcf
                       dir). NOT directory auto-discovery — that was judged too
                       easy to mis-point and flood the queue. A comment block
                       in the script header shows how to generate the map.
  2. Incremental      : fresh build by default; `update` as a 4th positional
                       arg enables --genomicsdb-update-workspace-path for
                       sample waves (lupus cohort will grow).
  3. Scatter + gate   : one workspace per chromosome; selector arg accepts a
                       single chrom | `autosomes` | `all`. Testing starts with
                       chr22.
  4. Scratch          : build on /scratch, copy workspace back to output (this
                       step genuinely benefits — random-access I/O).
  5. Mito notation    : `chrM` is the standard; auto-fallback to `chrMT` with a
                       warning if the data uses that.
  6. Engine           : committed to GenomicsDB (not CombineGVCFs) — cohorts
                       only grow, and the incremental-update feature is the
                       reason.

  ENGINE CAVEAT — GenomicsDB is NOT TileDB-VCF. GATK's GenomicsDBImport is built
  on GenomicsDB (an embedded, older TileDB core maintained by the Broad), not the
  standalone TileDB-VCF library (TileDB Inc.). They share the sparse-array idea
  and a TileDB lineage but are different codebases with different teams. Do NOT
  assume a TileDB-VCF feature (native S3/object-store I/O, lossless BCF
  round-trip, documented incremental-ingest semantics) applies to what
  GenomicsDBImport does — verify against GATK's own docs/behaviour. GenomicsDB
  was chosen for "done first": officially supported GATK step, unblocks S05/S06
  immediately, no new tooling. Revisit once S05/S06 are stable (section 5).

  NOT yet built (deferred until S04 is proven on FENIX with real data):
    * a GENDBI.seq_batch-slurmer.sh wrapper to scatter the per-chrom jobs
      (S04 itself can loop chromosomes serially in one process for now).
    * integration into bin/supp/run_pipeline.sh / PIPELINE.single_sample.sh
      (S04 is a cohort-level step, not single-sample — needs its own launcher).

  Added 2026-08-31 for the JAGUAR chr22 test (test/jaguar_chr22/):
    * Truncation guard — S04 checks each GVCF for the BGZF EOF marker and warns
      (GENDBI_STRICT_GVCF=true to hard-fail). GenomicsDBImport is ALL-OR-NOTHING
      per invocation: one bad GVCF fails the entire wave, and none of that
      wave's samples are imported. Earlier waves' workspace is untouched
      (update works on a scratch copy).
    * S04 knobs are now env-overridable (GENDBI_READER_THREADS default
      $SLURM_CPUS_PER_TASK, GENDBI_BATCH_SIZE, GENDBI_JAVA_MEM) so a launcher
      can vary resources per run.
    * check_setup.sh flags the two known config problems automatically:
      bgzipped ref_gnm (GATK -R rejects it) and a missing .dict.

      re-import with action=update (GenomicsDB keeps the newer copy).

        wave 1  create +47 (47)   460 min import + ~4 s consolidate  (7h40m total)
        wave 2  update +46 (93)   445 min import + ~815 min CONSOLIDATE
                                  -> 1260 min GATK, 21h01m step time
  * CONSOLIDATION IS THE PROBLEM. On `create` (single fresh fragment) it is a
    ~4 s no-op. On `update` it merges fragments across the WHOLE db: chr1 to 93
    samples = ~13.5 h. That is WORSE than a full `create` rebuild of 93 samples
    (~15 h import, trivial consolidate). So:
      -> updates NEVER consolidate now (launcher wave_consol = wave 1 only).
         GenotypeGVCFs reads a multi-fragment db fine.
      -> if you truly want one fragment, REBUILD with `create` (all current
         samples), do not GENDBI_CONSOLIDATE=true an update.

    chromosomes an update+consolidate would time out. Another reason to drop it.

    for 46 samples) is the same rate as wave 1's create (7h40m for 47). The 3x
    is 100% the consolidation tail (13h35m). Without --consolidate, wave 2 would
    have been ~8h ≈ wave 1.

[TASK: pipeline-wide pre-flight checker]  (requested by maintainer 2026-08-31)
    The test/jaguar/check_setup.sh pattern proved very useful for the S04
    JAGUAR run — a fast, read-only PASS/WARN/FAIL sweep that catches environment
    and input problems before a job is ever submitted. Generalize it into a
    reusable pipeline-wide setup checker that other lab users can run.

    Scope / ideas:
      * one entry point, e.g. bin/supp/check_env.sh [step] [inputs...], that
        checks whatever the requested step needs and skips the rest.
      * shared library of check helpers (module load + tool version, config
        parse, reference .fa/.fai/.dict, bgzip/BGZF-EOF integrity, tiny-file
        outliers, index presence, scratch writable, disk space, SLURM sanity).
        Factor the helpers out of check_setup.sh so S04's checker and the
        pipeline-wide one share code.
      * per-step input contracts (01 FASTQ pairs, 02 sort.bam, 03 bqsr.bam,
        04 chrom_gvcf dirs + sample map, 05 gendb workspaces, 06 VQSR
        resource bundle — the last is also the S06 config gap in section 1).
      * keep it read-only and side-effect free; exit non-zero on any FAIL;
        keep the [PASS]/[WARN]/[FAIL] + summary format users liked.
      * wire it into PIPELINE.single_sample.sh / run_pipeline.sh as a
        preflight gate (opt-out flag), and document a standalone
        "run this before you start" invocation in INSTRUCTIONS.md.
      * LESSON from TEST03 (SLE cohort): never assume an input FILENAME encodes
        the sample name or a fixed directory depth — different cohorts/batches
        name things differently (see the S04 GenomicsDBImport TEST03 note
        above). Discover by structure (a known marker filename/dir like
        chrom_gvcf/, globbed) and confirm identity from file CONTENT (GVCF/BAM
        header) wherever possible, never by parsing the path.


[TASK: evaluate TileDB-VCF as a Script 04 replacement]  (backlog — important,
    NOT urgent; do NOT block S05/S06 on this)

    Rationale: true incremental sample ingest (vs GATK's update path that its own
    tracker says needs a backup — see section 1), native object-storage support,
    and a documented lossless VCF/BCF export path.

    FIRST STEP before any design work: confirm TileDB-VCF is available on FENIX
    (`module avail`, package repo). If it is not installed, this becomes a
    module-request to cluster admin — that has its own lead time and may itself
    justify staying on GenomicsDB for now.

    Counterargument to weigh before committing:
      * The scaling case for TileDB-VCF (Intel/Broad benchmarks: near-linear to
        ~40K samples, ~2 s to add a sample) is built around cohorts far larger
        than ours (SLEmx ~127, JAGUAR 93). At this scale GenomicsDB's "N+1" cost
        may already be small in absolute terms.
      * Switching ingestion tooling mid-pipeline is a real cost: new dependency,
        its own `tiledbvcf` CLI / Python API instead of GATK's Java tool, and a
        docs + CLAUDE.md rewrite for Script 04.
      * Not yet benchmarked against our ACTUAL FENIX runtimes — do a timing
        comparison on a real batch before committing, not a literature-only
        decision.
      * The per-chromosome SLURM launcher for S04 (section 4, "NOT yet built")
        should probably wait on this decision rather than be built twice — a
        TileDB-VCF rework would change the ingestion tooling it wraps.
